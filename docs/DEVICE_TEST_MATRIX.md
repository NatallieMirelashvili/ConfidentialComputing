# Device-side test matrix

Tests run by `optee_example_confidential_iot_tests` inside the QEMU guest. See
`docs/ATTESTATION_TESTING.md` §2a for how to build and run them.

## Tests

### `[1] UUID mimicry - a TA signed with a non-project key must not load`

* **Objective** - Only a TA signed with the project's private key can load, including one that claims the genuine TA's UUID.
* **Verification method and success condition** - Build a second, minimal TA through the same build pipeline but signed with a non-project key, then attempt three loads: **(b)** open the rogue by its own UUID; **(c)** copy the rogue over the genuine TA's file and open the *genuine* UUID; **(d)** restore, then flip one byte inside the genuine TA's payload and open it — (b) and (c) fail the header signature check, (d) fails the payload hash check the signed header carries. **Pass:** all three sessions are refused (`TEEC_ERROR_SECURITY`, `0xffff000f`), and a session to the genuine TA opens successfully twice as a control — leg **(a)** before any file is modified, and once more after the final restore, so a failed restore cannot be mistaken for a pass.
* **Related files** - `project/optee_examples/confidential_iot/tests/host/ta_tests.c` (`test_uuid_mimicry`); `project/optee_examples/ciot_rogue_ta/ta/Makefile` (the `override TA_SIGN_KEY` line) and `ta/attacker_ta.pem`; `keys/ciot_ta.pem`, `scripts/build.sh`, `scripts/verify-ta-signing.sh`; on the device, `/lib/optee_armtz/7d9f6d20-…-0001.ta` and `…-0003.ta`.

### `[2] Secure storage is scoped to the TA UUID`

* **Objective** - Objects the `confidential_iot` TA seals in secure storage are readable only by that TA, and the `sensor_link` PTA is reachable only from it and not from Normal World.
* **Verification method and success condition** - Load a second TA signed with the same project key as the `confidential_iot` TA — so it loads with equal privilege — but carrying a different UUID. Have it call `TEE_OpenPersistentObject` in `TEE_STORAGE_PRIVATE` on each of `ciot.ta.identity`, `ciot.sensor.psk` and `ciot.server.pubkey`, and read the object if any open succeeds. As a control, have the same TA create, read back and delete an object of its own under a separate id. Finally, attempt to open the `sensor_link` PTA from the Host process. **Pass:** all three opens return `TEE_ERROR_ITEM_NOT_FOUND` and no bytes are read; the control round-trip succeeds, showing the TA's storage is functional and the three failures are UUID scoping; and the PTA session is refused (`TEEC_ERROR_ACCESS_DENIED`, `0xffff0001`).
* **Related files** - `project/optee_examples/confidential_iot/tests/host/ta_tests.c` (`test_storage_scoping`); `project/optee_examples/ciot_probe_ta/ta/probe_ta.c` and `ta/include/ciot_probe_ta.h`; `project/optee_examples/confidential_iot/edge_device/ta/trusted_app.c` (the TA that seals the probed objects); `project/optee_os_ext/core/pta/sensor_link.c` and `project/optee_os_ext/lib/libutee/include/pta_sensor_link.h`; on the device, `/lib/optee_armtz/7d9f6d20-…-0004.ta`.

### `[3] Faked attestation - ta_sig cannot cover an attacker's ECDH key`

* **Objective** - The per-session signature the TA produces covers the ephemeral ECDH key that the TA itself generated, and cannot be made to cover a key held by the Host.
* **Verification method and success condition** - Acting as the server, read the TA's identity public key, then drive the evidence command with a caller-chosen nonce and ECDH key to obtain the TA's ephemeral public key, the transcript hash and the signature. Verify the signature with an independent implementation over the pre-image the server builds — `label ‖ nonce ‖ server_ecdh_pub ‖ device_ecdh_pub ‖ device_id` — and then over three substituted pre-images: one carrying a locally generated ECDH key in place of the TA's, one carrying a second session's nonce and key, and one carrying a different `device_id`. **Pass:** the returned transcript hash equals `SHA-256(nonce ‖ server_ecdh_pub ‖ device_ecdh_pub)`; the signature verifies over the unmodified pre-image; each session returns a different ephemeral key; and all three substituted pre-images fail verification. The test's own pre-image and digest routines are checked against fixed known-answer values first, so any later mismatch is attributable to the TA and not to the test.
* **Related files** - `project/optee_examples/confidential_iot/tests/host/ta_tests.c` (`test_fake_attestation`) and `tests/host/crypto_check.c` with `crypto_check.h`; `project/optee_examples/confidential_iot/edge_device/ta/trusted_app.c` (`ta_generate_attestation_evidence`, `sign_ta_identity`, `ta_generate_ta_identity`); `edge_device/ta/include/confidential_iot_ta.h`; `CC_Server/server/attestation.py` (`build_ta_identity_preimage`, `compute_ta_identity_msg`), which defines the pre-image the device must match.

### `[4] A lying Host gains nothing - the gates live in the TA`

* **Objective** - The Host cannot obtain protected sensor data by skipping attestation, by misreporting its result, or by completing a handshake against a server it controls.
* **Verification method and success condition** - From a session with no prior state, request protected sensor data; then attempt to complete the handshake without first running the key-exchange command; then run the key exchange properly and complete the handshake while presenting a locally generated server identity key together with a random signature; then request protected sensor data once more. **Pass:** the first data request is refused (`TEE_ERROR_BAD_STATE`); the out-of-order handshake is refused (`TEE_ERROR_BAD_STATE`); the handshake carrying the substituted server identity is refused — `TEE_ERROR_ACCESS_CONFLICT` if a server key is already pinned, `TEE_ERROR_SIGNATURE_INVALID` if none is pinned yet — and the final data request is still refused, showing no session key was derived. The presented signature is always random, never validly signed, so no run can cause an attacker key to be pinned.
* **Related files** - `project/optee_examples/confidential_iot/tests/host/ta_tests.c` (`test_host_cannot_fake_a_session`); `project/optee_examples/confidential_iot/edge_device/ta/trusted_app.c` (`ta_read_and_protect`, `ta_handshake_complete`, `authenticate_server`) and `edge_device/ta/trusted_app.h`; `edge_device/ta/include/confidential_iot_ta.h`; `CC_Server/server/crypto.py` (`sign_server_identity_raw`), which produces the signature the TA verifies.

### `[5] The sealed device identity cannot be re-badged or reshaped`

* **Objective** - The TA's identity keypair stays bound to the one `device_id` it was sealed with, can be re-exported but never re-pointed, and no malformed call from the Host can crash the TA or alter what it has stored.
* **Verification method and success condition** - In a single session, call the identity command twice with the device's real `device_id`, then once with a different `device_id`, then once more with the real one. Follow with a series of malformed calls: a zero-length and an over-length `device_id`, an undersized output buffer, an all-`NONE` parameter type word, an over-length nonce and an undersized ECDH point on the evidence command, and the retired and unknown command ids. Finish by reading the identity again. **Pass:** both initial reads return the same 65-byte public key; the differing `device_id` is refused with `TEE_ERROR_ACCESS_CONFLICT` and the following read still returns that same key; each malformed call returns the documented error (`TEE_ERROR_BAD_PARAMETERS`, `TEE_ERROR_SHORT_BUFFER` or `TEE_ERROR_NOT_SUPPORTED`); and the final read succeeds with the same key, showing the TA instance neither died nor lost state. Boundary values are set one byte beyond each documented limit, and the whole sequence shares one session so a crash cannot be masked by a fresh instance.
* **Related files** - `project/optee_examples/confidential_iot/tests/host/ta_tests.c` (`test_identity_is_immutable`); `project/optee_examples/confidential_iot/edge_device/ta/trusted_app.c` (`ta_generate_ta_identity`, `read_ta_identity_blob`, `TA_InvokeCommandEntryPoint`); `edge_device/ta/include/confidential_iot_ta.h` and `edge_device/ta/user_ta_header_defines.h`; `project/optee_examples/confidential_iot/scripts/provision-device.sh`, which relies on the command being idempotent; `CC_Server/server/device_registry.py`, which pins the exported key.

### `[6] The sensor key is pulled from the sensor, not injected by the Host`

* **Objective** - The Host can neither supply the Sensor Module's pre-shared key to the TA nor read the sealed one back. The key reaches the TA only over the secure UART, which Normal World cannot address.
* **Verification method and success condition** - Invoke the sensor-pairing command with each parameter shape capable of carrying key material: a memory reference input holding a caller-chosen 32-byte key, a memory reference output with a pre-zeroed buffer, and a value parameter. Then invoke it with no parameters, twice. **Pass:** all three shaped calls are refused with `TEE_ERROR_BAD_PARAMETERS`; the pre-zeroed output buffer is unchanged afterwards, showing the refusal happens before anything is written; and both parameterless calls return `TEE_SUCCESS`, the second confirming the command is idempotent and safe to run on every boot. `TEE_ERROR_ACCESS_DENIED` on a parameterless call indicates the Sensor Module has already served its one-time key and must be power-cycled.
* **Related files** - `project/optee_examples/confidential_iot/tests/host/ta_tests.c` (`test_sensor_psk_is_pulled`); `project/optee_examples/confidential_iot/edge_device/ta/trusted_app.c` (`ta_provision_sensor_secret`) and `edge_device/ta/include/confidential_iot_ta.h`; `project/optee_os_ext/core/pta/sensor_link.c` (`sensor_link_fetch_secret`) and `project/optee_os_ext/lib/libutee/include/pta_sensor_link.h`; `project/optee_examples/confidential_iot/sensor_module/sensor_daemon.c` (`handle_secret_request`); `scripts/pair-sensor.sh`, which burns the key into the Sensor Module.

## Security requirements covered

| Security requirement | Corresponding tests |
|---|---|
| Only TAs signed with the project's private key are allowed to run. | 1 |
| A TA binary that has been modified after signing does not run. | 1 |
| The secrets the `confidential_iot` TA seals in secure storage — its identity private key, the sensor pre-shared secret, and the pinned server key — cannot be read by any other code on the device. Test 1 closes the route of installing a TA at the same UUID; test 2 closes the route of reading them from a different UUID. | 1, 2 |
| Sensor readings cannot be taken directly off the secure UART by a Normal-World process; only the `confidential_iot` TA can open the `sensor_link` PTA. | 2 |
| The key used for the session key exchange can be shown to have been generated inside the TA. A key generated in Normal World cannot be passed off as the TA's, even when the TPM quote covering it is genuine. | 3 |
| The value the device presents for the TPM to quote is bound to that session's nonce and to both ECDH public keys. | 3 |
| Attestation evidence from one session cannot be reused in another session. | 3 |
| Attestation evidence produced by one device cannot be presented as another device's. | 3 |
| Protected sensor data is released only after attestation has actually completed. A Host that skips it, or misreports its result, obtains nothing. | 4 |
| The device derives a session key only for the server it is enrolled with; a substituted server identity is rejected by the TA, not by the Host. | 4 |
| A failed handshake leaves no usable session state behind. | 4 |
| A device's TA identity key stays bound to the `device_id` it was sealed with, so a copied secure-storage image cannot be presented under a different `device_id`. | 5 |
| Re-running provisioning re-exports the existing identity key rather than replacing it, so a device stays valid against its enrolled record across reboots. | 5 |
| Malformed or out-of-range parameters from the Host are rejected with a defined error and leave the TA running with its stored state intact. | 5 |
| The Sensor Module's pre-shared key never passes through Normal World: the Host can neither hand a key to the TA nor obtain the sealed one. | 6 |
| The Host cannot pair the device to a sensor of its own choosing, and repeated pairing attempts cannot replace the sealed key or force it to be fetched again. | 6 |
